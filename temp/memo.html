量化交易 H2 2026 Roadmap

現況診斷、優缺點盤點、下半年 priority、Claude / Codex 協作模型 — 2026-07-29 整理。 資料依據 docs/STRATEGY.md、docs/TRADING_PROFILE.md、 journal 紀錄與本週 TX 研究產出，未虛構任何數字。

01 現況老實話診斷

不是「原地踏步」，是卡在一個具體且可命名的階段。

Discretionary 憑感覺／經驗判斷，無固定規則
Systematic，未驗證 有固定規則，但 promotion 沒有重新做 OOS 你在這裡
Systematic + OOS 紀律 上線前強制 walk-forward／held-out 驗證
Portfolio 風控 Sharpe/Sortino/相關性/regime 全部量化管理

帳戶金額沒有反映努力，原因很具體：S1 現行版本 V3.9 是「backtest PF 變好、但沒有重新做 OOS 驗證」就被 promote 上線的 —— 連 spec 自己都寫了「Not separately restated」。對照它取代的 V3.7（PF 較低，但 OOS confirmed），等於是用一個驗證更弱的版本， 換掉了一個驗證更強的版本，只因為回測數字比較好看。這正是你自己懷疑的 ——「TradingView 每次重新優化、歷史績效就變好」—— 的確切定義：in-sample curve-fitting。在同一段歷史資料上反覆調參，模型學到的是「這段資料的雜訊」而不是 「市場的結構」。這種模式的 live 表現特徵是固定的：一開始（一月）剛好某段參數命中當時的 regime，看起來很神；之後只要 regime 一換，過擬合的參數就開始漏財 —— 小賺大賠，因為停損停利點位 是靠著剛好卡在歷史噪音上算出來的，換一個 regime 就全部失效。

02 S2 的版本史更誇張

V1.9 Failed OOS — 第一個上線版本，edge 不足
V3.2 Marginal — pooled OOS PF ≈ 1.11（幾乎打平成本），仍在跑 live risk 目前正式版
V4.1 OOS PF 1.64，比現行版更好，但從未 promote 放在架上沒用

Pooled OOS PF 1.11 扣掉滑點與手續費幾乎等於沒有 edge，卻仍在跑真實風險 —— 只是靠「每週上限 2 筆」這條帶子把傷害限縮，不是因為策略被證明有效。 更諷刺的是：OOS 表現更好的 V4.1（PF 1.64）沒有被 promote，等於你有一把更利的刀放在抽屜沒用， 卻拿著一把驗證不足的刀在砍。S1、S2 目前現行版本，沒有一個帶著剛重新做過的 OOS 驗證。

03 做得好的地方

不是安慰話 —— 這部分的成熟度在同規模個人交易者裡確實少見。

  • ✓ Private / Public 雙 repo 研究架構：每個 study 都有 study.json / results.json / source_manifest（來源 SHA-256 雜湊）/ decision_log / handoff， 自動化 verifier 做 cross-check。
  • ✓ rank_score 一律要求 Wilson 95% 信賴區間，不是裸勝率。
  • ✓ 本週新增的 TX 月季節性、費波那契回檔研究，樣本數小 （n=7-8）就誠實標記「descriptive, not decision-grade」，沒有硬拗成可交易訊號 —— 統計上的謙遜 做對了。
  • ✓ 交易哲學本身正確：高信心、低頻率，寧可零訊號也不硬凹。

你缺的不是紀律，是把這套紀律用在你真正在賭錢的 S1 / S2 身上。研究側的謙遜和嚴謹，還沒有回頭套用到扛真實曝險的策略 promotion 流程。

04 缺口盤點

項目狀態評估
Regime detection 完全缺 Macro rank-score／48 時段表都只是 advisory overlay，不區分「策略在哪個 regime 下才有效」。
Normalization / z-score 未見於策略邏輯 S1/S2 的驗證流程中沒有標準化處理，指標尺度未跨時間/跨商品對齊。
Sharpe / Sortino / drawdown 幾乎完全缺失 Repo 裡沒有聚合 equity curve、沒有半年滾動風險指標。「小賺大賠」的印象只存在你腦中和對帳單，系統裡查不到 —— 這是獨立的流程缺口。
Overfitting 評估 有能力，未套用於 live Spec 框架有能力做 walk-forward / deflated Sharpe / Monte Carlo permutation，但 S1 V3.9 的 promotion 決策裡完全沒走這一步 —— 最致命的一項，直接對應你自己的懷疑。
Regime-specific 有效性測試 缺 V3.9 沒有「在哪些 regime 下會失效」的紀錄。
策略分散 / 相關性 只有資金控管，非統計分散 S1+S2 併行有 combined risk cap（1.5%），但那是曝險上限，沒人量過 S1/S2 訊號相關性，TX 也還沒納入組合層級評估。

05 下半年 Priority Roadmap

照順序做，不要並行展開 —— 你自己說想簡單、想重複做簡單的事，這份清單就是照那個原則排的。

1

S1 V3.9 補做 walk-forward + OOS 重新驗證

扛主要曝險的策略，且是 spec 自己承認的已知缺口，投報比最高、風險最集中。切出訓練時未見過的 held-out 期間，重跑既有回測 pipeline，正式寫進 study.json / decision_log。若 OOS PF 明顯低於 1.888，要有心理準備降級或退回 V3.7 邏輯。必須排在任何新策略開發之前 —— 地基沒補之前蓋新樓，只是複製同一個錯誤。

現在就做 · 不開發新策略
2

把 Sharpe / Sortino / drawdown 做成週報固定產出

掛在既有的週報 workflow 上，不需要新系統，只是週報骨架加一節「風險調整後績效」。資料源是 journal —— 但目前 journal 只有兩筆真實紀錄，這也逼你把交易紀錄的 habit 補齊，等於順手解掉 另一個流程缺口。

06 Claude / Codex 協作模型

活動CadenceOverfitting 風險Guardrail
週報 固定・週頻 低 消費既有資料、整合輸出＋風險指標追蹤，不涉及參數調整，適合完全自動化。
請分析 固定・日/會話頻 低 純訊號讀取＋macro/時段 overlay 判讀，消費既有模型，不是重訓模型。
開發策略／回測／優化 固定・季頻（非隨興） 高 三者必須綁在一起處理：(1) promotion 到 formal/live 前，decision_log 必須有「重新 restate 的 OOS 結果」，缺這欄不准 promote；(2) 優化前先切好並鎖定 held-out 集，不能因為表現不好就換一批重測；(3) 不做 daily/on-demand，改固定季頻，避免「手癢重跑、 數字好看就上線」的循環。

老實講：如果回測和優化的做法跟 produce 出 V3.9 的方式一樣 —— 同一份歷史資料反覆調參、看回測數字進步就收工 —— 只會做出更多 V3.9 型態的問題，換個版本號而已。上面的 guardrail 是把 spec 既有的 Stage/handoff 機制， 從「建議」正式改成「gate」。

一句話總結 你不是缺技術，是缺一條「回測數字變好看 ≠ 可以上線」的硬規則 —— 先把這條線畫在 S1 V3.9 身上， 其他都等它做完再說。
